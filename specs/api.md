# Documentación de la API RESTful de Gestión de Turnos

Este documento describe la API RESTful para la gestión de turnos, diseñada para una aplicación de usuario único (profesional) que permite a los clientes reservar citas.

---

## 1. Protocolo de Comunicación, Autenticación y Manejo de Sesiones

### Protocolo de Comunicación
La API utiliza el protocolo **HTTPS** para todas las comunicaciones, garantizando la seguridad y encriptación de los datos. Se adhiere a los principios de REST, utilizando métodos HTTP estándar para operaciones CRUD sobre recursos y respondiendo con datos en formato **JSON**.

### Autenticación
La autenticación para el usuario profesional (administrador de los turnos) se realizará mediante **Email y Contraseña tradicional**. Tras un inicio de sesión exitoso, el servidor emitirá un **JSON Web Token (JWT)**.

*   El JWT deberá ser enviado en el encabezado `Authorization` de todas las solicitudes subsiguientes que requieran autenticación, utilizando el esquema `Bearer`.
    ```
    Authorization: Bearer <your_jwt_token>
    ```
*   El JWT tendrá un tiempo de expiración definido. Se recomienda implementar un mecanismo de **refresh token** para permitir sesiones prolongadas sin necesidad de re-login constante.

### Manejo de Sesiones
La API es **sin estado (stateless)**. El estado de la sesión se gestiona a través del JWT:

*   El cliente (aplicación web del profesional) almacenará el JWT (y opcionalmente el refresh token) de forma segura (e.g., `localStorage` o `HttpOnly cookies`).
*   Cada solicitud autenticada incluirá el JWT en el encabezado. El servidor validará la firma y la expiración del token con cada petición.
*   No hay "sesiones" almacenadas en el lado del servidor; la validez de un token es lo que determina la autenticación.

## 3. Estructura de Errores Comunes

La API devolverá respuestas de error estandarizadas en formato JSON para facilitar el manejo de errores por parte del cliente. Se utilizarán los códigos de estado HTTP apropiados.

### Formato de Error
```json
{
  "status": 400,
  "code": "BAD_REQUEST",
  "message": "Mensaje de error legible para el usuario.",
  "details": [
    {
      "field": "email",
      "message": "El formato del email no es válido."
    },
    {
      "field": "password",
      "message": "La contraseña debe tener al menos 8 caracteres."
    }
  ]
}
```
*   `status`: (Integer) El código de estado HTTP.
*   `code`: (String) Un código interno de la API que identifica el tipo de error (opcional pero recomendado para manejo programático).
*   `message`: (String) Un mensaje descriptivo y legible por humanos del error.
*   `details`: (Array de Objetos) Información adicional sobre el error, especialmente útil para errores de validación, indicando campos específicos y sus problemas.

### Ejemplos de Errores Comunes

| Código HTTP | Código Interno (Ejemplo) | Descripción                                                                   |
| :---------- | :----------------------- | :---------------------------------------------------------------------------- |
| `400 Bad Request` | `VALIDATION_ERROR`       | Los datos de la petición son inválidos (e.g., formato incorrecto, campos faltantes). |
|             | `INVALID_ARGUMENT`       | Uno o más parámetros de la solicitud son incorrectos o fuera de rango.      |
| `401 Unauthorized`| `AUTHENTICATION_FAILED`  | No se proporcionaron credenciales o son inválidas.                          |
|             | `TOKEN_EXPIRED`          | El token de autenticación ha expirado.                                      |
| `403 Forbidden`   | `ACCESS_DENIED`          | El usuario autenticado no tiene permisos para realizar esta acción.         |
|             | `ALREADY_BOOKED`         | El slot de tiempo solicitado ya está ocupado.                               |
| `404 Not Found`   | `RESOURCE_NOT_FOUND`     | El recurso solicitado no existe.                                            |
| `409 Conflict`    | `CONFLICT_ERROR`         | La solicitud entra en conflicto con el estado actual del servidor (ej: intentar reservar un turno ya reservado, o eliminar un servicio con turnos activos). |
| `422 Unprocessable Entity` | `BUSINESS_RULE_VIOLATION` | La solicitud es sintácticamente correcta, pero no puede ser procesada debido a reglas de negocio (ej: intentar cancelar un turno fuera del plazo permitido). |
